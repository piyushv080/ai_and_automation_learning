# Prometheus and Grafana Guide

This beginner-friendly guide explains monitoring with Prometheus, visualization with Grafana, and metric collection with Node Exporter. It also walks through a small lab on an Amazon EC2 instance.

## What is monitoring?

Monitoring is the continuous process of collecting, analyzing, and visualizing system and application metrics to understand performance, availability, and overall health.

Monitoring answers questions such as:

- Is the server running?
- How much CPU and memory are in use?
- Is disk space running out?
- Is the application responding?
- When did performance change?
- Who should be notified when a threshold is crossed?

Metrics are numeric measurements collected over time, such as CPU usage percentage, free memory bytes, request count, or response latency.

## Prometheus and Grafana at a glance

| Tool | Main purpose |
| --- | --- |
| Prometheus | Collects and stores time-series metrics and evaluates alerting rules. |
| Grafana | Queries data sources and visualizes metrics in dashboards. |
| Node Exporter | Exposes Linux host metrics for Prometheus to scrape. |
| Alertmanager | Groups, routes, silences, and sends alerts generated by Prometheus. |

Prometheus watches and stores the data. Grafana makes that data easy to explore and understand.

## What is Prometheus?

Prometheus is a free and open-source monitoring and alerting toolkit. It collects metrics from configured targets, stores them as time-series data, and provides a query language called PromQL.

Prometheus can monitor:

- Servers and virtual machines.
- Applications instrumented with client libraries.
- Containers and Kubernetes workloads.
- Databases and message queues through exporters.
- Cloud and network services through exporters or integrations.

Prometheus is pull-based: it periodically requests metrics from an HTTP endpoint exposed by each target.

## What is Grafana?

Grafana is a free and open-source visualization and dashboard platform. It does not store the monitoring data itself; it connects to external data sources such as Prometheus, PostgreSQL, Elasticsearch, CloudWatch, or Loki, then displays the results as graphs, gauges, tables, and alerts.

A useful way to remember the difference:

- Prometheus collects and stores metrics.
- Grafana queries and visualizes them.

## Why use Prometheus and Grafana together?

Using both tools gives you a practical monitoring stack:

1. Prometheus scrapes metrics such as CPU, memory, disk, and network usage.
2. Prometheus stores the values with timestamps.
3. Grafana queries Prometheus and displays the results in dashboards.
4. Prometheus rules and Alertmanager notify people when something needs attention.

Grafana can also combine metrics with logs, traces, and business data from other sources, but this guide focuses on the Prometheus integration.

## How Prometheus works

1. Prometheus reads its configuration file and discovers scrape targets.
2. It sends an HTTP request to each target's metrics endpoint, usually `/metrics`.
3. Exporters or instrumented applications return metric samples.
4. Prometheus stores the samples with labels and timestamps in its local time-series database.
5. You can query the data through the Prometheus web UI, the HTTP API, or Grafana.
6. Prometheus evaluates alerting rules and sends firing alerts to Alertmanager.

Important concepts:

- **Target:** an endpoint Prometheus scrapes.
- **Job:** a named group of targets with the same purpose.
- **Sample:** a value at a point in time.
- **Label:** a key-value pair that identifies a time series, such as `instance`, `job`, or `env`.
- **Exporter:** a service that exposes metrics in Prometheus format.
- **PromQL:** Prometheus Query Language.
- **Scrape interval:** how often Prometheus collects metrics.

Prometheus is efficient for multidimensional time-series data, but it is not a general-purpose log store or a long-term data warehouse. Use appropriate retention, remote storage, or a dedicated long-term metrics system when needed.

## How Grafana works

1. Grafana connects to one or more data sources.
2. It sends queries to those data sources.
3. It renders the returned data as panels in a dashboard.
4. Dashboards can be shared, organized, and made interactive with variables.
5. Grafana can display alerts, but Prometheus or another alerting engine usually evaluates the underlying rule.

Grafana data sources are not limited to Prometheus. Common examples include:

- Prometheus for metrics.
- Loki for logs.
- Tempo or Jaeger for traces.
- PostgreSQL or MySQL for relational data.
- Elasticsearch for search and log data.
- CloudWatch for AWS metrics.

## What is Node Exporter?

Node Exporter is a Prometheus exporter for Linux and Unix host metrics. Install it on each server you want to monitor. It exposes hardware and operating-system metrics such as:

- CPU usage.
- Memory usage.
- Disk space and filesystem usage.
- Network traffic.
- Load average.
- System uptime.
- Kernel and host information.

Node Exporter listens on port `9100` by default and exposes metrics at:

```text
http://<node-address>:9100/metrics
```

Prometheus scrapes that endpoint, stores the samples, and Grafana visualizes them. Node Exporter monitors the host; it does not automatically instrument application business metrics.

## Lab architecture

A small EC2 lab can use one monitoring server and one or more monitored nodes:

```text
+---------------------------+
| Monitoring server         |
|                           |
|  Prometheus  :9090        |
|  Grafana     :3000        |
|  Node        :9100        |
+-------------+-------------+
              |
              | private network or restricted access
              |
+-------------+-------------+
| Managed node              |
|  Node Exporter :9100      |
+---------------------------+
```

For a first lab, it is acceptable to run Prometheus, Grafana, and Node Exporter on the same EC2 instance. For anything beyond a lab, separate the components appropriately and restrict access.

## Security warning before exposing ports

Prometheus and Node Exporter do not provide strong built-in authentication or TLS. Grafana has authentication, but it should still be protected.

Do not open these ports to the entire internet:

- `9090`: Prometheus.
- `9100`: Node Exporter.
- `3000`: Grafana.

Use a security group rule limited to your administrator IP, a VPN, or a private network. For production, place the tools behind a reverse proxy with TLS and authentication, use private subnets, and follow your organization's access-control requirements.

## Install Prometheus on an EC2 instance

The commands below use an official Prometheus release tarball. Replace the example version with the current release from the official downloads page. Use a current Amazon Linux, RHEL, Ubuntu, or Debian AMI.

Set the version and download the release:

```bash
PROM_VERSION="3.5.0"   # replace with the current release
ARCH="amd64"
cd /tmp

curl -LO "https://github.com/prometheus/prometheus/releases/download/v${PROM_VERSION}/prometheus-${PROM_VERSION}.linux-${ARCH}.tar.gz"
tar xzf "prometheus-${PROM_VERSION}.linux-${ARCH}.tar.gz"
cd "prometheus-${PROM_VERSION}.linux-${ARCH}"
```

Install the binaries and configuration:

```bash
sudo install -m 0755 prometheus promtool /usr/local/bin/
sudo mkdir -p /etc/prometheus /var/lib/prometheus
sudo cp -r consoles console_libraries /etc/prometheus/
sudo cp prometheus.yml /etc/prometheus/prometheus.yml

sudo useradd --system --no-create-home --shell /usr/sbin/nologin prometheus 2>/dev/null || true
sudo chown -R prometheus:prometheus /etc/prometheus /var/lib/prometheus
```

Create a systemd unit:

```bash
sudo tee /etc/systemd/system/prometheus.service >/dev/null <<'EOF'
[Unit]
Description=Prometheus
Wants=network-online.target
After=network-online.target

[Service]
User=prometheus
Group=prometheus
Type=simple
ExecStart=/usr/local/bin/prometheus \
  --config.file=/etc/prometheus/prometheus.yml \
  --storage.tsdb.path=/var/lib/prometheus \
  --web.listen-address=:9090
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
EOF

sudo systemctl daemon-reload
sudo systemctl enable --now prometheus
```

Check the service:

```bash
sudo systemctl status prometheus
sudo journalctl -u prometheus -n 50 --no-pager
curl http://localhost:9090/-/healthy
```

If you use trusted distribution packages instead, use the package names and service units provided by that distribution. The original lab used older RPM repositories; do not copy an obsolete `el/7` repository into a current system.

## Install Node Exporter

Download and install Node Exporter on each monitored Linux host:

```bash
NODE_VERSION="1.9.0"   # replace with the current release
ARCH="amd64"
cd /tmp

curl -LO "https://github.com/prometheus/node_exporter/releases/download/v${NODE_VERSION}/node_exporter-${NODE_VERSION}.linux-${ARCH}.tar.gz"
tar xzf "node_exporter-${NODE_VERSION}.linux-${ARCH}.tar.gz"
sudo install -m 0755 "node_exporter-${NODE_VERSION}.linux-${ARCH}/node_exporter" /usr/local/bin/
sudo useradd --system --no-create-home --shell /usr/sbin/nologin node_exporter 2>/dev/null || true
```

Create the service:

```bash
sudo tee /etc/systemd/system/node_exporter.service >/dev/null <<'EOF'
[Unit]
Description=Prometheus Node Exporter
Wants=network-online.target
After=network-online.target

[Service]
User=node_exporter
Group=node_exporter
Type=simple
ExecStart=/usr/local/bin/node_exporter --web.listen-address=:9100
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
EOF

sudo systemctl daemon-reload
sudo systemctl enable --now node_exporter
```

Verify the metrics endpoint locally:

```bash
curl http://localhost:9100/metrics | head
sudo systemctl status node_exporter
```

Restrict port `9100` in the security group to the Prometheus server or a trusted administration network.

## Configure Prometheus

Prometheus configuration lives in `/etc/prometheus/prometheus.yml`. The most important section for collecting metrics is `scrape_configs`.

Start with a simple configuration:

```yaml
global:
  scrape_interval: 15s
  evaluation_interval: 15s

scrape_configs:
  - job_name: prometheus
    static_configs:
      - targets:
          - localhost:9090

  - job_name: node_exporter
    static_configs:
      - targets:
          - localhost:9100
```

If Prometheus is on a different host from Node Exporter, use the monitored host's private address or DNS name:

```yaml
  - job_name: node_exporter
    static_configs:
      - targets:
          - node01.example.test:9100
          - node02.example.test:9100
        labels:
          environment: lab
```

Keep the YAML indentation consistent. Do not use tabs.

Validate the configuration:

```bash
promtool check config /etc/prometheus/prometheus.yml
```

Restart Prometheus to apply the change:

```bash
sudo systemctl restart prometheus
```

If lifecycle reload is enabled, you can reload instead:

```bash
curl -X POST http://localhost:9090/-/reload
```

Open the Prometheus UI:

```text
http://<prometheus-host>:9090
```

Check the **Status > Targets** page. The `prometheus` and `node_exporter` targets should be `UP`. If a target is `DOWN`, check the address, port, firewall, security group, and whether the exporter is running.

Run a first query from the **Graph** page:

```promql
up
```

Then try:

```promql
node_cpu_seconds_total
node_memory_MemAvailable_bytes
```

`up` returns `1` for a reachable target and `0` for an unreachable target.

## Alertmanager overview

Prometheus evaluates alerting rules. Alertmanager receives firing alerts and handles:

- Grouping related alerts.
- Deduplication.
- Silencing during maintenance.
- Inhibition to suppress lower-priority alerts.
- Routing to email, Slack, Microsoft Teams, PagerDuty, or webhooks.

Alertmanager does not collect metrics. It is a separate service that works with Prometheus.

A simple alerting rule:

```yaml
groups:
  - name: node-health
    rules:
      - alert: NodeExporterDown
        expr: up{job="node_exporter"} == 0
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "Node Exporter target is down"
          description: "Prometheus has failed to scrape a node exporter for 5 minutes."
```

A production Alertmanager setup needs a receiver configuration, secrets management, tested routing, and an escalation policy. Keep email passwords, webhook tokens, and SMTP credentials in a secret manager or protected configuration, not in the Git repository.

## Install Grafana on an EC2 instance

Use the official Grafana RPM repository on a RHEL-compatible system:

```bash
sudo tee /etc/yum.repos.d/grafana.repo >/dev/null <<'EOF'
[grafana]
name=grafana
baseurl=https://rpm.grafana.com
repo_gpgcheck=1
enabled=1
gpgcheck=1
gpgkey=https://rpm.grafana.com/gpg.key
sslverify=1
sslcacert=/etc/pki/tls/certs/ca-bundle.crt
EOF
```

Install and start Grafana:

```bash
sudo dnf install -y grafana
sudo systemctl enable --now grafana-server
sudo systemctl status grafana-server
```

Grafana listens on port `3000` by default.

```text
http://<grafana-host>:3000
```

The initial login is commonly `admin` / `admin`. Change the password immediately when prompted. Do not leave the default password in place, especially on any host reachable from a network.

For production:

- Put Grafana behind TLS, preferably with a reverse proxy.
- Restrict port `3000` to trusted networks.
- Create named users or use SSO.
- Disable anonymous access unless it is explicitly required.
- Apply least-privilege roles and teams.
- Keep Grafana and its plugins current.

## Add Prometheus as a Grafana data source

1. Sign in to Grafana.
2. Open **Connections > Data sources**.
3. Select **Add data source**.
4. Choose **Prometheus**.
5. Set the Prometheus server URL:
   - Same host: `http://localhost:9090`
   - Different host: `http://<prometheus-private-address>:9090`
6. Keep the default scrape and query settings unless you have a specific reason to change them.
7. Select **Save & test**.

A successful test shows a message such as `Data source is working`.

If the test fails, verify that Grafana can reach Prometheus on the network, that Prometheus is listening on the expected address, and that port `9090` is allowed only from approved sources.

## What is a dashboard?

A dashboard is a collection of panels that display monitoring data in real time. Panels can show:

- Time-series graphs.
- Gauges.
- Stat values.
- Tables.
- Bar charts.
- Heatmaps.

A good dashboard answers a specific operational question. It should have clear units, a useful time range, understandable labels, and links to logs or runbooks where appropriate.

## Create a Grafana dashboard

1. Open the dashboard menu.
2. Select **New > Dashboard**.
3. Select **Add visualization** or **Add new panel**.
4. Choose the Prometheus data source.
5. Enter a PromQL query.
6. Select **Run query**.
7. Choose the visualization type.
8. Configure the title, unit, legend, thresholds, and color.
9. Save the dashboard with a descriptive name.

Useful PromQL starting points:

### Target availability

```promql
up
```

### CPU usage percentage

```promql
100 - (
  avg by (instance) (
    rate(node_cpu_seconds_total{mode="idle"}[5m])
  ) * 100
)
```

### Memory used percentage

```promql
100 * (
  1 - (
    node_memory_MemAvailable_bytes
    /
    node_memory_MemTotal_bytes
  )
)
```

### Filesystem space available

```promql
node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"}
```

### Network receive rate

```promql
rate(node_network_receive_bytes_total{device!="lo"}[5m])
```

### System load

```promql
node_load1
```

For each panel, set the correct unit. For example, use percent for CPU and memory percentages, bytes for free space, and bytes per second for network throughput.

## Dashboard design tips

- Put the most important health signals at the top.
- Use consistent color meanings and units.
- Show the same time range across related panels.
- Avoid displaying every available metric at once.
- Use variables such as `instance` or `environment` to filter dashboards.
- Add links to runbooks, logs, and service ownership information.
- Import community dashboards from trusted sources, but review the queries and data source assumptions first.
- Treat dashboards as code when possible; provision them through version-controlled configuration.

## Troubleshooting

### Prometheus service does not start

```bash
sudo systemctl status prometheus
sudo journalctl -u prometheus -n 100 --no-pager
promtool check config /etc/prometheus/prometheus.yml
```

Check the configuration path, file permissions, storage directory ownership, and whether another process is using port `9090`.

### Target is DOWN in Prometheus

```bash
curl http://localhost:9100/metrics
ss -lntp | grep 9100
sudo systemctl status node_exporter
```

Check the target address, DNS, security group, firewall, and whether Prometheus can reach the target on the configured port.

### Grafana shows no data

- Confirm the Prometheus data source test succeeds.
- Confirm the dashboard time range includes recent data.
- Run the same query in the Prometheus UI.
- Check that the target is `UP`.
- Check whether the metric name and labels match the actual data.
- Check the Grafana query editor for errors.

### Node Exporter metrics are missing

- Verify Node Exporter is running.
- Confirm `/metrics` returns data.
- Confirm the Prometheus scrape configuration uses the correct host and port.
- Confirm the target's clock is synchronized; large clock skew can make time-series queries confusing.

### Disk fills up

Prometheus stores data locally. Monitor `/var/lib/prometheus` and configure retention based on available disk and operational requirements. For example, set a retention period in the service command:

```text
--storage.tsdb.retention.time=15d
```

For long-term retention, use a supported remote-write or long-term storage design rather than assuming local disk is unlimited.

## Production and security checklist

- [ ] Ports `9090`, `9100`, and `3000` are not exposed to the public internet.
- [ ] Security groups allow only approved administrator or monitoring networks.
- [ ] Prometheus and Node Exporter are placed behind a reverse proxy, mTLS, or private networking where required.
- [ ] Grafana uses TLS, strong authentication, and least-privilege roles.
- [ ] The default Grafana admin password has been changed.
- [ ] Alertmanager credentials and webhook tokens are stored securely.
- [ ] Prometheus storage has enough capacity and a tested retention policy.
- [ ] Backups and restore procedures exist for dashboards and monitoring configuration.
- [ ] Configuration is managed as code and reviewed before production changes.
- [ ] Alert rules are tested so that real incidents notify the right people.
- [ ] Dashboards have clear units, ownership, and links to runbooks.
- [ ] Metric labels are bounded; avoid high-cardinality values such as raw user IDs or request payloads.
